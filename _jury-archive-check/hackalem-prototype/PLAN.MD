# План прототипа автопротоколирования совещаний

## Цель на один день

Сделать воспроизводимый прототип, который принимает запись совещания из Teams, Zoom или Google Meet и выдает редактируемый протокол: транскрипт с говорящими, саммари по темам, поручения с ответственными и сроками, экспорт PDF и DOCX. Проверить работу на трех имеющихся обезличенных записях: русской, казахской и смешанной русско-казахской речи.

Подключение бота к живой конференции, рассылки, СЭД, дашборд исполнения и голосовая идентификация не входят в однодневную версию. Источник аудио выделяется в отдельный модуль, чтобы позже подключить live-адаптеры платформ без переписывания обработки.

## Принцип размещения и приватности

- Демонстрационная машина NVIDIA Brev находится в облаке, поэтому на нее загружаются только записи, уже обезличенные и разрешенные для такого использования. Это не считается размещением в закрытом контуре заказчика.
- Все распознавание, диаризация, извлечение поручений и генерация саммари выполняются локальными моделями на этой машине. Аудио и текст не отправляются в OpenAI API, облачный Supabase или другие внешние сервисы.
- Интерфейс и API слушают только `127.0.0.1`; доступ с компьютера разработчика идет через SSH-туннель. Публичную ссылку на приложение не создавать.
- Файлы и база хранятся локально; содержимое аудио и транскриптов не пишется в логи. В интерфейсе есть удаление встречи вместе с исходным файлом и результатами.
- Для переноса в закрытый контур нужны контейнеры/зависимости и заранее скачанные веса моделей. Рабочий тракт должен запускаться без сетевых запросов; исходящий сетевой доступ можно заблокировать.

## Архитектура и стек

```text
Запись MP4/M4A/MP3/WAV/WebM
    -> FastAPI: загрузка, метаданные, статус задачи
    -> FFmpeg: извлечение моно-аудио 16 кГц
    -> faster-whisper: транскрипт и временные метки
    -> pyannote: интервалы говорящих
    -> объединение реплик по времени
    -> локальная LLM: темы, факты, проблемы, поручения, саммари
    -> React: проверка и исправления секретарем
    -> DOCX/PDF
```

| Компонент | Выбор для прототипа |
| --- | --- |
| Интерфейс | React + TypeScript + Vite; после сборки отдается FastAPI с того же адреса |
| Backend | Python + FastAPI + Pydantic; один фоновый обработчик задач, без отдельной очереди |
| Подготовка аудио | FFmpeg; единый формат для файлов из трех платформ |
| Распознавание | `faster-whisper` + локальная Whisper large-v3, без принудительного выбора одного языка для всей встречи |
| Диаризация | локальная `pyannote/speaker-diarization-community-1`; имена говорящих подтверждаются человеком |
| Анализ текста | локальная `qwen3:8b` через Ollama; структурированный JSON проверяется Pydantic |
| Хранение | SQLite и локальный каталог файлов; одна встреча обрабатывается за раз |
| Экспорт | `python-docx`; PDF через локальное преобразование LibreOffice, с кириллическими и казахскими шрифтами |

Для Brev выбрать одну доступную GPU с не менее чем 22 ГБ VRAM, 32 ГБ RAM и 60 ГБ свободного диска; ориентиры по классу GPU: A10G, L4 или лучше в пределах бюджета. Проверить загрузку всех моделей до демонстрации. Если памяти не хватит для одновременной работы, последовательно запускать этапы и освобождать GPU между ними.

Модели загружаются при подготовке окружения, а при обработке используются локальные пути. Доступ к весам pyannote требует предварительно принять условия модели; токен нужен только на этапе загрузки и не сохраняется в репозитории. Облачные кредиты OpenAI и hosted Supabase в приложение не интегрировать.

## Поток данных и интерфейсы

1. Пользователь загружает запись, задает название, дату и часовой пояс встречи. Для версии первого дня ограничить длительность 15 минутами и размер файла 200 МБ, чтобы время обработки было предсказуемым.
2. Backend сохраняет запись локально и создает задачу со статусом `queued`, `processing`, `ready` или `failed`. Ошибка этапа видна в интерфейсе без вывода чувствительного содержимого в логи.
3. ASR возвращает реплики с началом и концом. Диаризация назначает им `speaker_1`, `speaker_2` и т. д. При перекрытии голосов или неоднозначной привязке реплика помечается для проверки.
4. LLM группирует реплики по темам, выделяет показатели и проблемы, формирует поручения. Каждое поручение содержит текст, ответственного либо `не указан`, исходную формулировку срока, нормализованную дату при ее однозначности, ссылку на реплику и метку `требует проверки`.
5. Пользователь сопоставляет номера говорящих с именами, исправляет текст и поручения, затем утверждает результат. Говорящий, произнесший поручение, и ответственный за его выполнение хранятся отдельно.
6. Экспорт строится только из подтвержденного состояния. Удаление встречи удаляет запись, транскрипт, поручения и экспортированные файлы.

Минимальный API: загрузка встречи, чтение статуса, чтение результата, сохранение правок говорящих/реплик/поручений, скачивание PDF/DOCX и удаление встречи. Будущий live-адаптер должен подавать аудио с метками времени на вход того же модуля обработки; в первый день сетевой поток и WebSocket не реализуются.

## Формат саммари и протокола

Ориентир оформления -- приложенные примеры протоколов. Экспорт и экран проверки используют одну структуру данных:

1. **Шапка:** название, дата, участники (если известны), отметка о машинной подготовке и проверке секретарем.
2. **Саммари по ключевым пунктам:** короткий вводный абзац и таблица `Направление / доклад | Показатель | Проблема`. В таблицу попадают только факты, произнесенные на встрече. Отсутствующий показатель обозначается `Не указан`.
3. **Темы встречи:** для каждой темы заголовок вида `Тема 1 -- ...`, короткий абзац с ключевыми цифрами, контекстом и проблемой, затем таблица `Поручение | Ответственный | Срок`.
4. **Подробный транскрипт:** приложение к протоколу с временем и говорящими. Поручения на экране связаны с исходной репликой; по нажатию открывается соответствующее место записи.

Заголовки документа -- синие, таблицы -- с тонкой сеткой и светлой заливкой заголовков, как в примерах. Таблицы должны переносить длинный текст и не обрезать строки. Краткое саммари пишется по-русски, при этом цитаты и транскрипт сохраняют исходный язык и смешанные фразы. Модель не должна придумывать показатель, решение, ответственного или срок. Относительные сроки вроде `в пятницу` переводятся в дату только от явно заданной даты и часового пояса встречи; исходная формулировка сохраняется.

## План работ на 10-12 часов

| Время | Результат и контрольная точка |
| --- | --- |
| Час 0-1 | Поднять Brev, проверить GPU и доступ через SSH-туннель, подготовить три обезличенные записи и загрузку моделей. |
| Часы 1-3 | Получить реплики с временем и говорящими хотя бы для одной записи; проверить казахскую и смешанную речь на коротких фрагментах. |
| Часы 3-5 | Получить структурированные темы, показатели, проблемы и поручения; сверить имена, сроки и цитаты на всех трех записях. Если Whisper заметно теряет поручения на казахском, сравнить с локальной казахско-русской моделью Sybyrla и оставить вариант с меньшим числом ошибок в поручениях. |
| Часы 5-8 | Собрать API и два экрана React: загрузка/статус и проверка транскрипта/саммари/поручений с правками. |
| Часы 8-10 | Экспорт PDF/DOCX, удаление встречи, обработка ошибок, инструкция запуска и описание архитектуры в README. |
| Часы 10-12 | Пройти три сквозных сценария, проверить отображение обоих форматов и провести репетицию показа. |

Правило приоритета: к концу пятого часа должен работать путь от файла до черновика протокола без интерфейса. Если настройка моделей задержится, сокращать декоративную часть интерфейса, сохраняя проверку человеком, оба экспорта и сквозной сценарий.

## Критерии готовности к показу

- Каждая из трех записей загружается и приводит к транскрипту, саммари и поручениям без облачных API.
- Реплики имеют время и метку говорящего; пользователь может назначить говорящему имя и исправить ошибочную привязку.
- У каждого найденного поручения видны ответственный, срок или отметка об отсутствии срока, а также исходная реплика. Исправления попадают в экспорт.
- PDF и DOCX содержат сводную таблицу по направлениям и разделы по темам с таблицами поручений; казахские и русские символы отображаются корректно.
- README описывает запуск на Brev и в закрытом контуре, подготовку весов для работы без сети, требования к оборудованию, ограничения прототипа и порядок демонстрации.
- Перед показом выполнен ручной прогон трех языковых сценариев, а ошибки распознавания имен, дат и поручений честно зафиксированы.
